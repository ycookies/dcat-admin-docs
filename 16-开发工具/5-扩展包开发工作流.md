# 扩展包开发工作流

本文是一套**标准化的扩展包开发流程**，从业务讨论到上线发布，分 6 个阶段推进。它既适合开发者照着做，也适合作为 **AI（如 Claude、Trae）一句话指令开发扩展包的执行规范**。

> 配合技能包里的完整引导文档 `extension-workflow.md` 使用，本文是其精简导读。

## 一句话触发

对 AI 说出下面这句话，它就按本文档执行全流程：

```text
开发 <系统名>，讨论确认功能后，按扩展包开发工作流完成开发上线。
```

例如：`开发 内容管理系统，讨论确认功能后，按扩展包开发工作流完成开发上线。`

换业务只需改 `<系统名>`，流程不变。

## 两把生成器的分工

整个流程贯穿两个命令，职责清晰，不要混用：

| 命令 | 用在哪一阶段 | 产出 |
|------|--------------|------|
| `admin:ext-make-pro` | 阶段 1（开包，只用一次） | 扩展骨架 + 数据层（Model/Migration/Seeder）+ 开发蓝图文档 |
| `admin:scaffold --extension=` | 阶段 2、阶段 4（反复用） | 后台 Controller、API 控制器、Resource |

**铁律：写业务代码（Controller / Resource）一律走 `admin:scaffold`，不要手写骨架。**

## 阶段 0 · 业务讨论（必做，不要跳过）

目标：和需求方对齐"开发什么"，形成可追溯的文字记录，避免边写边改。

需要确认：
- 系统/扩展的中文名、用途、目标用户；
- 核心功能模块清单（每个模块对应一张或多张表）；
- 是否需要移动端接口（C 端 member-api / 管理端 admin-api）；
- 是否要发布到应用市场。

**产物**：在对话里形成「功能模块 + 数据表」草案（模块名 → 表名 → 关键字段），复述确认后才进入阶段 1。

> 例：用户说"开发内容管理系统"，应产出："文章管理→articles 表(title/content/cover_image/status)；分类管理→categories 表(name/sort)；是否需要小程序端文章接口？" 然后等确认。

## 阶段 1 · 创建骨架 + 数据层

### 1.1 创建扩展包

```bash
php artisan admin:ext-make-pro <vendor>/<name> \
  --models=<表名，逗号分隔> \
  --seed \
  --blueprint
```

命令说明：
- `--models`：表已存在则**反推**生成 Model + Migration；表不存在则生成**占位**骨架。
- `--seed`：生成幂等 Seeder（带 mock 数据）。
- `--blueprint`：生成 `docs/` 蓝图文档（传了 `--models` 会自动开）。
- `--table-prefix=`：新建表的表名前缀（默认从包名自动缩写，如 `miniapp_manager` → `miniapp_`）。反推的已存在表不加前缀。

创建后执行迁移：

```bash
php artisan admin:ext-update <vendor>.<name>
```

### 1.2 完善数据层

打开 `docs/database/schema.md`，按字段约定把每张表的字段补全：
- 每个字段加 `->comment('业务说明')`；
- 状态/枚举字段加 `@scaffold:options={"0":"禁用","1":"启用"}`；
- 金额用 `decimal`（禁 float），布尔用 `boolean`；
- 建立关联（`user_id` 等外键）与索引。

**每新增/修改一个迁移文件，必须登记进 `version.php`，否则不执行。**

### 自检
```bash
php artisan admin:ext-update <vendor>.<name>   # 迁移执行成功，无报错
# 进数据库确认表已创建、字段/注释正确、seeder 幂等
```

## 阶段 2 · 后台 CRUD

> **铁律：所有 Controller / Grid / Form / Show 用 `admin:scaffold --extension=` 生成，禁止手写骨架。**

```bash
php artisan admin:scaffold \
  --table=<表名1>,<表名2> \
  --extension=<vendor>/<name> \
  --force
```

命令自动生成 Model / 后台 Controller / Lang / 路由 / 菜单 / 权限。字段语义识别靠阶段 1 的字段注释（`@scaffold:type` / `@scaffold:options`），所以**字段注释写得好，生成的控件就准**。

生成后补充脚手架做不了的人工项：
- 关联下拉：`$form->select('user_id')->options(User::pluck('name','id'))`；
- 上传配置：`->disk('public')->dir('xxx')`；
- 富文本：`$form->editor('content')`；
- Grid 调优：筛选器、快捷搜索、列显示器。

### 自检
- 后台能访问每个模块的列表/新增/编辑/详情/删除，权限正常。

## 阶段 3 · 业务逻辑

按需实现（不是每个扩展都要）：
- 表单 `saving`/`saved` 事件钩子（如密码加密、库存扣减）；
- Repository、模型作用域（`scopeXxx`）；
- 自定义 Action（批量操作、行操作）；
- 中间件。

## 阶段 4 · 接口开发（带 --api 时）

> **铁律：member-api / admin-api 控制器与 Resource 用 `admin:scaffold --extension= --api/--admin-api` 生成，禁止手写骨架。**

```bash
# 一次生成后台 + 双端 API + Resource（最常用）
php artisan admin:scaffold \
  --table=<表名> \
  --extension=<vendor>/<name> \
  --api --admin-api --resource --force
```

生成 member-api / admin-api 控制器（继承 `BaseApiController`）+ Resource 类 + API 路由。

生成后必须人工补充：
1. **补全 `getValidationRules()`**——脚手架留的是空实现，必须按业务填 `store`/`update` 的校验规则；
2. Scramble 接口注释（方法 PHPDoc、validate 字段行内注释）；
3. 按业务裁剪默认的列表/批量/导入导出接口——不是每个表都需要全套 RESTful；
4. **同步维护 `docs/delivery/api_delivery.md`**——这是移动端开发的唯一数据源，写清 base URL、请求/响应契约、枚举字典。

### 自检
- 访问 `/docs/admin-api`、`/docs/member-api`，接口文档与代码一致；
- 用 curl/Postman 跑通核心接口（登录→拿 token→调业务接口）。

## 阶段 5 · 发布上线

1. 完善 `README.md`（安装、配置、使用说明）；
2. 若 `--marketplace`：完善 `docs/MARKETPLACE.md`，把 `<!-- AI_PROMPT -->` 占位换成真实截图；
3. `composer.json` 元信息（name/description/authors）准确；
4. 交付检查（对照 `docs/tasks/PLAN.md` 末尾的「交付检查清单」）：
   - 所有迁移在 `version.php` 登记，`ext-update` 干净执行；
   - 后台 CRUD 全部可访问、权限正确；
   - 接口交付文档与实际一致；
   - seeder 幂等；
5. 打 Tag 发布。

### 自检
- 在干净环境 `php artisan admin:ext-install <vendor>.<name>` 能从零跑通。

## 全程铁律

1. **迁移**：`updates/` 下具名类、无 namespace、无时间戳前缀，必须登记 `version.php`。Seeder 必须幂等。
2. **禁用** `php artisan migrate` / `migrate:fresh` / `db:seed` 改库结构；扩展迁移走 `admin:ext-update` / `admin:ext-install`。
3. **业务代码用脚手架生成**：后台 CRUD（阶段 2）、member-api/admin-api/Resource（阶段 4）一律用 `admin:scaffold --extension=` 生成骨架，生成后只做人工打磨。
4. **每完成一阶段**：更新 `docs/tasks/PLAN.md` 勾选项，并简述「当前阶段 / 上一步完成 / 下一步」。这是"做到哪了"的唯一事实来源。
5. **表名前缀**：新建表必须带扩展前缀（见阶段 1），反推表保持原名。
